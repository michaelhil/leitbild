---
name: planning-advice
description: Use for maintenance or delivery schedules, completion deadlines, crew alternatives, and explaining whether work can finish in time
allowed-tools: [workspace_explore, workspace_call, conversation_read]
---

Answer planning questions through Planning's discovered operations and current owner evidence. A feasibility or what-if question authorizes generating recorded alternatives; it does not authorize changing authored inputs, weakening rules, committing a baseline or operating World.

1. Resolve the focused Plan and read `planning.plan.read` summary, then the deciding jobs, rules, crews/purchases and options. Preserve its revision. Interpret the user's deadline using the plan's date and time zone; state that interpretation. Ask only when materially ambiguous. Find the job whose completion includes all requested work and return-to-service tests; never guess its key. A soft target is distinct from the user's requested deadline.
2. Reuse fresh options only when they cover the exact question. For a requested deadline, each reusable alternative must carry that exact due rule. Otherwise use `planning.plan.generate` with `keep:true` and deadline what-ifs: each adds `also:[{kind:"due",key,job,finishBy,words,source}]` using the discovered schema and user-request source. Compare the existing crew (`buy:[]`) with permitted purchases (`buy:"allowed"`), respecting any user cost or crew restriction. For a cheapest qualifying option, use the actual extra-cost goal's index as `lead:{goal:index}`. Do not substitute the example's target time or edit its inputs. Keep the original comparison and report any owner retention limit.
3. Check each returned status and freshness. A fresh validated schedule meeting the hard deadline supports "can", conditional on the authored assumptions. Only an actual `proven infeasible` result establishes impossibility for its checked alternatives; unresolved, cancelled or invalid input proves neither outcome. Never relabel a late soft target as a missed hard deadline. A deadline outside the modeled window needs an explicit scope explanation; do not move the window or silently round the requested time.
4. Read `planning.plan.explain` for the deciding finish/crew dependency or refusal. Give a direct answer, the modeled finish in local time, the required crew/purchase and cost, and the reason. For a refused deadline, distinguish its proof from the earliest retained feasible reference; call that reference "earliest checked" unless optimality is actually established. Refresh World inputs only when current plant conditions are needed, then regenerate stale options. Planning does not apply maintenance or isolation to World.
5. Show the actual option through `planning.plan.display`, including a refused deadline when relevant; it can show a separately identified feasible reference. Inspect the returned status/coverage and use its returned `viewRef` in one `leitbild-view` block. Do not invent dates in a drawing, claim a reference meets the refused deadline, or create a calculation script as a substitute for the scheduling solver. Keep the answer brief; the owner view provides the schedule and evidence.
