---
name: planning-advice
description: Use for maintenance or delivery schedules, completion deadlines, crew alternatives, and explaining whether work can finish in time
allowed-tools: [workspace_explore, workspace_call, conversation_read]
---

Answer planning questions through Planning's discovered operations and current owner evidence. A feasibility or what-if question authorizes generating recorded alternatives; it does not authorize changing authored inputs, weakening rules, committing a baseline or operating World. Scheduled reviews, releases and acceptance tasks are forecasts, never evidence that a person gave authorization.

1. Find the Plan. In a Room scoped to a World Run or its family, first open the focused Run's own plan: call `planning.plan.create` on the plan Definition in scope with `{demoRun: <that Run's id>}`, its schema's guided-run input. This creates the plan when missing and returns that Run's own plan as `target` (beside a copy, the copy's plan). Open at most once per question: each open of an existing plan writes a history entry. If the open is refused, report the refusal and present no schedule as current. With no plan Definition in scope, use only a Plan `about` the focused Run; if there is none, say plainly that no plan exists for this scenario. Never use a Plan `about` another Run without naming that Run. Elsewhere, resolve the focused Plan.
2. Read `planning.plan.read` summary and sources. A current feasibility question needs current World values before generating or reusing options. Where `planning.sources.refresh` is offered (a Workspace-scoped Room), call it first with the Plan id. Beside a Run it is not offered: count the open as a new World read only if `planning.plan.create`'s description says opening an existing plan reads World again; otherwise say the plan's World values are as stored and when they were read (the summary's `refreshedAt`). Pass the current revision as `expectedRevision` beside `input` on each refresh/generate call. Unless the question is explicitly historical, never rely on old recorded plant state, even in the same conversation. If a refresh or open changed values, schedules published earlier are not current. Then read the actual revision and deciding jobs, rules, crews/purchases and options. Follow needed `more` pages with `cursor`; include calendars and each crew's permitted work. Interpret the deadline using the plan's date and time zone; state that interpretation. Ask only when materially ambiguous. Find the completion job including all requested work and return-to-service tests; never guess its key. A soft target is distinct from the requested deadline.
3. Reuse fresh options only when they cover the exact question. For a requested deadline, each reusable alternative must carry that exact due rule. Otherwise use `planning.plan.generate` with `keep:true` and deadline what-ifs: each adds `also:[{kind:"due",key,job,finishBy,words,source}]` using the discovered schema and user-request source. Compare the existing crew (`buy:[]`) with permitted purchases (`buy:"allowed"`), respecting any user cost or crew restriction. For a cheapest qualifying option, use the actual extra-cost goal's index as `lead:{goal:index}`. Do not substitute the example's target time or edit its inputs. Keep the original comparison and report any owner retention limit.
4. Check each returned status and freshness. A fresh validated schedule meeting the hard deadline supports "can", conditional on the authored assumptions. Only an actual `proven infeasible` result establishes impossibility for its checked alternatives; unresolved, cancelled or invalid input proves neither outcome. Never relabel a late soft target as a missed hard deadline. A deadline outside the modeled window needs an explicit scope explanation; do not move the window or silently round the requested time.
5. Read `planning.plan.explain` for the deciding finish/crew dependency or refusal. Follow its `more` pages with `cursor`. Its finish chain explains this checked order; do not infer all critical work from zero float, or treat missing `limiting` as no gain. Resource gain is a diagnosis, not a permitted purchase. Use `why-start` for a job's joint causes. Ground reported times in its owner-localized `lines` and actual schedule rows. ISO timestamps ending `Z` are UTC; convert them to the plan's time zone, never relabel their clock as local. Give a direct answer, the modeled finish in local time, the required crew/purchase and cost, and the reason. For a refused deadline, distinguish its proof from the earliest retained feasible reference; call that reference "earliest checked" unless optimality is actually established. Regenerate stale options. Planning does not apply maintenance or isolation to World.
6. For an estimate or release-time what-if, use `planning.plan.edit` with `preview:true` on the selected option. This re-times its saved order; it is not a new optimization. Report the owner's consequence and rule findings. A movement list may be partial: never invent omitted rows. Do not save an assumption change just to answer a what-if or supply a person's authority. The retained display still shows the saved schedule, not this unsaved preview.
7. Show the actual option through `planning.plan.display`, including a refused deadline when relevant; it can show a separately identified feasible reference. Inspect the returned status/coverage and use its returned `viewRef` in one `leitbild-view` block. Do not invent dates in a drawing, claim a reference meets the refused deadline, or create a calculation script as a substitute for the scheduling solver. Keep the answer brief; the owner view provides the schedule and evidence.
