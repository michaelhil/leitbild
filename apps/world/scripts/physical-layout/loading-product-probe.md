# Full-product loading proof

From `apps/world`, run:

```
LEITBILD_LOADING_TESTED_COMMIT=<built-app-commit> bun scripts/physical-layout/loading-product-probe.ts <isolated-qa-run.json> <evidence-directory>
```

The Run URL must be loopback and already paused. The runner changes local view
state only. It opens its own fresh Chrome profile and closes it in `finally`.
The supplied app commit identifies the separately built/running product; the
runner commit and observer hash are recorded independently. A runner checkout
does not identify a remote or separately built app by itself.

The fixed Halden workload demands all five admitted layouts in the initial and
fresh-owner site browser. Five is this retained scenario's assertion, never a
production admission/count cap. It then focuses the full Unit 1 turbine hall
and measures first/return 3D operating, Stack, cutaway, Plan operating/lower,
and fresh-browser-owner transitions. Forced GC precedes the named return cases.
The distant map after closing the browser has legitimately no detail draw; it
is an owner boundary, not a fabricated detail-loading time.

The old product helper sleeps 700 ms after a floor selection and 500 ms after
scope selection. This proof has no fixed settlement sleep. It timestamps the
actual event dispatch in the World frame, follows prepared-response typed-array
identity through `bufferData`, attribute-0 VBO/VAO and a real TRIANGLES draw of
the requested semantic key. A microtask fence follows the rendering task, so
Plan composition precedes it. It reports first matching draw and observed GPU
completion separately. These are not physical-monitor presentation timestamps.

Worker source post/first-result/termination and preparation post/result are
recorded separately. Preparation response includes queue, CPU and transfer;
the product has no public controller-ready timestamp. GPU buffers may be old
even when CPU preparation has repeated, so current matching preparation replies
and original VBO preparation timestamps are distinct fields.

Only primitive metadata and weak keys are retained by instrumentation. It must
not pin typed arrays during forced GC. Draw-wrapper overhead is reported; other
wrappers also add some overhead. Baseline and candidate must use the identical
observer hash, dimensions, browser/GPU and retained source/workload. HTTP presence
and layout-read starts/responses/failures are passively recorded through CDP.
Selected-owner freshness is checked separately after geometry completion from
the product's validated live-status text, not inferred from geometry readiness.

Reject a result on missing/mismatched view draw, failed/unfinished physical
worker/source job, GL error, exception, missing owner freshness or failed all-site
bootstrap. No geometry, quality, visibility, source identity or count reduction
is permitted as an optimization. Final candidate qualification additionally
requires the existing temporal flicker DPR1/DPR2 and real-gap controls, source
invariance, CPU geometry/pick equivalence when relevant, and resource/lease tests.

Calibration failures and final timing receipts use separate directories. Do not
compare historical retained-engine timings with this full-product protocol.
