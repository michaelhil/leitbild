# Agents progressively discover scoped Workspace operations

Every AI Agent receives the same two-tool Workspace interface. `workspace_explore` returns compact, current Resources and Definitions inside the Room Scope and searches their advertised operations. It includes schemas only when requested. `workspace_call` uses the exact operation id and target returned by exploration for both reads and changes, and can batch independent reads. The Agent decides what evidence it needs; no fixed lookup sequence, call count, or Pack-specific integration flow is encoded.

The Room Scope is resolved against the live Workspace catalog on every call. A Workspace scope includes the Workspace operations and its current Resources and Definitions. A Resource scope includes that Resource and its source Definition. A collection scope derives current membership from `contains` and `member-of` links, so an `all except` Run Family automatically includes future copies while a `selected only` scope remains fixed. Exact references are copied unchanged between discovery and invocation. Focused Subjects are filtered to the current scope and indicate attention only.

Operation descriptions, kinds, risks, applicability, and JSON schemas are the progressive-discovery vocabulary. A Module may add `searchTerms` to an operation when important Pack-owned vocabulary is otherwise hidden behind it, such as the names and expansions of choices in a nested action catalog. The broker only performs literal word matching and does not interpret acronyms, infer aliases, assign confidence, or treat search terms as identifiers or authority. Search terms are omitted from the compact result; the advertised read operation returns the canonical choices and IDs.

Capability schemas describe the actual JSON wire values, including branded identifiers. Literal multi-term search is shared across World discovery surfaces, but domain vocabulary and canonical identifiers remain Pack-owned. Expected input, target, and work-limit rejections are caller outcomes, not Pack-health failures. A caller-supplied retry key is valid only when an operation explicitly advertises `acceptsIdempotencyKey`; semantic `idempotent` metadata alone does not imply transport support.

“Discover”, “inspect”, and “act” are not separate access classes: they are reads or changes advertised as operations. The broker checks scope and live applicability, while the target Module owns validation, concurrency, safety, and any current restrictions. This avoids duplicated authority labels, Agent-stored Resource ids, eager state dumps, universal query languages, broker-side response filtering, and Pack-specific clients in Agents.

The assistance Skill routes live questions to Workspace operations and implementation questions to product sources, advises the Agent to establish high-signal orientation, retrieve related evidence together when useful, answer in useful stages, and dig deeper when it materially improves the result. It treats shorthand as a possible meaning, retrieves canonical IDs instead of guessing, reuses stable identifiers already established in conversation, rereads volatile state, and resolves material ambiguity before changing state. These are judgment aids, not a workflow engine.

Context efficiency is achieved by compact, filterable producer responses and by requesting schemas only for likely calls—not by hiding evidence or limiting Agent intelligence. The final complete LLM request remains inspectable. Message telemetry records cumulative provider token/cache counters, model and tool call counts, each tool result's encoded byte size, and nested Workspace-operation success. This makes evidence bloat and recovery loops measurable without adding context to the model request or duplicating every intermediate prompt.
